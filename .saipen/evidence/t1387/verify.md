## Two checks that did not work, and why they are recorded

An AST source scan was the first instrument and it failed twice.

1. **Blind.** A sink-directed scan (walk `setText` / `addItem` / `drawText` /
   `setToolTip` arguments) reported PASS on the *pre-fix* tree. The negative
   control caught it. The raw literal never reaches a sink as itself: it is
   built into a local, then interpolated into a `tr()` template by `.format()`.
   A direct-argument check structurally cannot see that class.
2. **Noisy.** Scanning every string literal in the three files instead
   produced 455 findings pre-fix and 452 post-fix — a real delta of 3 buried
   in CSS fragments, palette keys and dict subscripts. Not a gate.

So the shipped check is behavioural, not lexical.

## A tool defect found while committing this ticket

`git diff --numstat` on the 33 locale packs read `1861 1852` each — every line
of every pack "changed" — for a nine-key merge. The packs were not corrupted:
loading both sides and comparing showed 9 keys added, 0 removed, `_meta`,
`coverage_pct` and `missing_keys` all identical, key order preserved.

The cause was `tools/i18n_apply_campaign.py:160-161`, which wrote each merged
pack with `indent=1` in text mode, while every committed pack is
`json.dumps(..., indent=2, ensure_ascii=False)` with LF endings (verified:
`indent=2 reproduces HEAD exactly: True`; indent 1, 4 and `None` do not). Text
mode also turned `\n` into `\r\n` on Windows.

Fixed to `indent=2` and `newline="\n"`, then the packs were reset to HEAD and
the campaign re-run. Every pack is now `10 1` — the 9 new keys plus the last
line gaining a trailing comma — which is reviewable. Left unfixed, every
future campaign would keep doing this.

`tools/i18n_verified_identical.json` had the same problem from this session's
own verdict writer, and was corrected the same way: `11 0`, nothing removed.
