T-1383 -- Core disposition of saihunt/HUNT-001: REJECTED
============================================================

Ticket verify: "Independently reproduce or reject hypothesis, record Core
disposition, apply no package patch during intake."

Hypothesis under review
-----------------------
  "saipen sub sync|spawn|adopt source the shared contract from
   STATE.saipen_home, so every worker is provisioned from a home the runtime
   is not executing."

Disposition: REJECTED. The premise ("a home the runtime is not executing") is
true; the conclusion ("therefore every worker is provisioned wrongly") does
not follow, because the file that carries the worker contract is not shipped by
the executing install at all. The proposed repair -- source the contract from
the runtime instead of STATE.saipen_home -- would make spawning refuse.

No package patch was applied during intake, per the ticket.

2. Why the engine reads the contract from STATE.saipen_home
------------------------------------------------------------
  tools/saipen.py:3335
      saipen_home = state.get("saipen_home") or ""
  tools/saipen.py:3389/3394/3398
      sub_sync/sub_spawn/sub_adopt all receive that value

  saipen_engine/subs.py:2482
      template_root = Path(saipen_home) / "extensions" / "subs" / "TEMPLATE"
  saipen_engine/subs.py:2497
      role_source = Path(saipen_home) / "extensions" / "subs" / f"{name}.md"

  Both are guarded refusals when the tree is absent. Sourcing them from HOME
  would hit, on every spawn:

      REFUSE [VALIDATION_FAILED] saipen_home ... has incomplete subSaipen
             TEMPLATE; clone/refresh before spawning

      REFUSE [VALIDATION_FAILED] no role evidence to anchor spawn of ...
             ROLE_EVIDENCE_UNAVAILABLE

  So reading the contract from the project's install is the only path that
  works. This is a required input, not a defect.


3. The voice contract is deliberately the opposite choice
-----------------------------------------------------------
  saipen_engine/state.py:589  running_style_token()   -> reads the running
      install's STYLE.md.
  saipen_engine/subs.py:2525/2817                       -> workers are
      stamped with that token.

  saipen_engine/state.py:594 installed_style_token(saipen_home=None)
      "`saipen_home` is accepted and IGNORED: the running installation owns the
       voice contract. ... 'the pointer is stale' is not evidence that it did
       [read the current contract]."

  The asymmetry is documented and intentional: file PROVENANCE is project-pinned
  (reproducible per project), the voice CONTRACT is runtime-current (proves the
  writing agent read the live STYLE.md). The hypothesis treats this as one
  undifferentiated "shared contract" sourced by one rule.

5. The one real difference, and why it is not this ticket
----------------------------------------------------------
  STYLE.md differs between the two homes. That is the direct cause of the
  refusal recorded in T-1376 evidence:

      REFUSE [VALIDATION_FAILED] subSaipen STATE is malformed: style_contract
             'ded-6b950e75' does not match the installed STYLE.md marker
             'ded-71fc58de'

  It was NOT caused by the contract being read from the wrong install: the
  worker was stamped with the running token at spawn time, and the running
  STYLE.md has since changed. `sub sync`/`sub spawn` re-stamp the token from the
  running install, which is why re-spawning during the T-1376 drain succeeded.

  A voice-contract divergence between two installs is a real condition and is
  worth the engine owner knowing, but it is a different subject from HUNT-001,
  it is not reachable from this project, and re-homing it under T-1383 would
  misfile it.
