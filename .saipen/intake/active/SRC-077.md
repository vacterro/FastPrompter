## Request

LIMISAW / FastPrompter / ZAICODE / AUDAPACK

ЗАДАЧА

Нужно хирургически реализовать полноценную поддержку второго независимого Google Antigravity Pro аккаунта одновременно в четырёх проектах:

- LIMISAW
- FastPrompter
- ZAICODE
- AUDAPACK

У пользователя теперь действительно есть второй Google-аккаунт с отдельной Google AI Pro подпиской. Цель не состоит в переключении одного аккаунта после исчерпания другого и не состоит в обходе квот.

Нужны два реально независимых Antigravity execution contexts, которые:

1. могут быть авторизованы разными Google-аккаунтами;
2. могут существовать одновременно;
3. независимо показывают свои лимиты;
4. независимо запускаются;
5. не перетирают авторизацию друг друга;
6. могут использоваться параллельно;
7. одинаково идентифицируются во всех четырёх приложениях;
8. не требуют повторной ручной настройки одного и того же аккаунта в каждом приложении.

Пользователь уже сформулировал исходный запрос примерно так:

"У меня есть второй Google-аккаунт с Pro подпиской. Нужно грамотно добавить его в лимит-метр так же, как другие аккаунты, затем видеть его в FastPrompter и ZAICODE, а также при необходимости открывать как второй аккаунт через AUDAPACK. Проверить весь путь и сделать вход во второй аккаунт."

Это USER-EXPLICIT CROSS-REPO TARGET.

Не уходить в другие backlog-задачи.

============================================================
ВАЖНЕЙШАЯ НАХОДКА И ROOT CAUSE
============================================================

Не реализовывать второй Antigravity аккаунт простым добавлением второй директории или второй UI-строки.

В текущих исходниках Antigravity всё ещё фактически одноаккаунтный на уровне авторизации.

На Windows текущий Antigravity CLI использует глобальный Windows Credential Manager credential target:

gemini:antigravity

Следовательно:

- ~/.gemini/antigravity
- ~/.gemini/antigravity-2
- дополнительный data_dir
- дополнительный profile_locator
- дополнительный AccountRef
- дополнительная UI-карточка

САМИ ПО СЕБЕ НЕ СОЗДАЮТ ВТОРОЙ АККАУНТ.

Если оба экземпляра запускают обычный:

agy -p "/usage"

в одном Windows user/keyring context, они читают один и тот же активный Google credential.

Такой вариант запрещён к реализации, потому что он создаст ложную multi-account поддержку.

КРИТИЧЕСКИЙ ИНВАРИАНТ:

ОДНА ВИЗУАЛЬНАЯ УЧЁТНАЯ ЗАПИСЬ ANTIGRAVITY =
ОДИН РЕАЛЬНО НЕЗАВИСИМЫЙ AUTH/EXECUTION CONTEXT.

Если это невозможно доказать, второй аккаунт нельзя показывать как независимый.

============================================================
ЕСЛИ ANTIGRAVITY НЕ ИМЕЕТ PROCESS-LOCAL MULTI-ACCOUNT
============================================================

Если текущий Antigravity CLI действительно поддерживает только один:

gemini:antigravity

на Windows user context, НЕ ДЕЛАТЬ credential swapping основным механизмом.

Запрещён canonical design вида:

1. сохранить token A;
2. заменить gemini:antigravity на token B;
3. запустить;
4. вернуть token A.

Причины:

- race condition;
- два параллельных worker'а сломают друг друга;
- refresh token может измениться;
- crash оставит неправильный credential;
- секреты окажутся под управлением нашего приложения;
- meter может прочитать не тот аккаунт;
- AUDAPACK может запустить не тот account;
- невозможно гарантировать корректную concurrent работу.

Также не тащить сторонний credential-switcher как обязательную dependency.

Если process-local namespace отсутствует, использовать настоящий независимый OS/keyring context.

На Windows это может означать отдельный Windows logon/security context для второго Antigravity.

Но:

- не создавать Windows пользователя без явного согласия оператора;
- не сохранять Windows пароль в plaintext;
- не использовать runas /savecred автоматически без отдельного согласия;
- сначала исследовать более чистые поддерживаемые варианты.

Если для безопасного второго context действительно требуется отдельный Windows user, подготовить этот путь и остановиться на OPERATOR_REQUIRED перед созданием пользователя/вводом credentials.

============================================================
ОБЯЗАТЕЛЬНЫЙ LIVE ACCEPTANCE
============================================================

После unit/integration tests провести реальную операторскую проверку.

ЭТА ЧАСТЬ КРИТИЧНА.

Нужен второй настоящий Google account с Pro.

Сначала account A:

- подтвердить login;
- получить /usage;
- сохранить безопасный fingerprint/snapshot metadata.

Затем account B:

- запустить отдельный verified context;
- пользователь вручную проходит Google login;
- получить /usage.

После этого:

1. одновременно показать A и B в LIMISAW;
2. одновременно показать A и B в FastPrompter;
3. одновременно показать A и B в ZAICODE;
4. увидеть оба в AUDAPACK;
5. запустить A из AUDAPACK;
6. запустить B из AUDAPACK;
7. убедиться, что это разные authenticated contexts;
8. снова снять /usage A;
9. снова снять /usage B;
10. убедиться, что ни один login не перезаписал другой.

Дополнительная сильная проверка:

запустить небольшую работу только через B.

После обновления quota:

- изменение должно быть видно на B;
- A не должен менять identity из-за B.

Не требовать, чтобы числовые quota были различными в каждый момент времени.
Они теоретически могут случайно совпадать.

Доказывать независимость по execution context и повторной идентичности, а не по одному числу процентов.
