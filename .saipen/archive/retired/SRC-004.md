## STATUS: TARGETED HEAVY-SILO SWITCH AUDIT — COMPLETE

Главный вывод: **переключение должно быть navigation hot path, а сейчас оно частично работает как save + reconcile + document rebuild + rendering pass.** На маленьких силосах это незаметно. На больших начинает пахнуть именно тем диалогом Windows, который у тебя на скриншоте.

1. **FREEZE-001 — P0: переключение PROJECT TAB синхронно прогоняет ВСЕ связанные силосы.**
   `src/fastprompter/main.py:14398-14401`:

   ```python
   self.commit_current_text()
   self._push_sync_files()
   ```

   А `slots=None` в `_push_sync_files()` буквально означает:
   `main.py:5577-5580` → reconcile **EVERY bound silo**.

   Дальше цикл `main.py:5610-5629` проходит по каждому связанному силосу и делает:

   ```python
   digest = self._sync_side_digest(text)
   ```

   А `_sync_side_digest()` в `5386-5394` делает полный:

   ```python
   text.encode(...)
   hashlib.blake2b(...)
   ```

   То есть если проект набит жирными silos, при обычном щелчке вкладки GUI thread хеширует весь связанный объём проекта. Worker занимается записью на диск, но **решение, что писать, всё ещё вычисляется синхронно в UI**. Для fresh binding ещё хуже: `main.py:5642` делает синхронный `read_text_file()`.

   Исправление: **PROJECT TAB navigation вообще не должна вызывать `_push_sync_files(slots=None)`**. Перед уходом надо публиковать только реально dirty owners. Нужен `dirty_sync_slots`/generation set. Полный reconcile оставить только explicit Save / shutdown / repair-команде. Digest желательно считать worker-ом либо переиспользовать по `(slot_generation, content_revision)`.

   `theme_mixin.py:433-477`.

   Для документа больше 500 блоков включается:


   Звучит солидно, почти nagu päris оптимизация. Но в `markdown_highlighter.py:319-381` degraded mode отключает в основном:

   * code sub-rules;
   * conceal markers.

   А основной цикл:

   ```python

       for match in pattern.finditer(text):
   ```

   на `360-378` продолжает выполняться.

   В `_highlighting_rules` сидит куча regex: bold, underline, strike, italic, H1/H2/H3, hashtags, inline code, quote, Markdown links, URLs, images, HR, checkboxes, lists и прочая святая инквизиция.


   То есть при переходе на огромный silo производится full-document rehighlight прямо в GUI.


   но **эта переменная нигде больше не используется**. То есть аварийный выключатель уже нарисован на стене, просто провод к нему никто не подключил. Великолепие цивилизации.

   Исправление должно быть трёхуровневым:
   `rich` для небольших документов, настоящий `degraded essentials` для средних, и `huge` для примерно `>=500k chars` или большого block count, где full rehighlight при navigation запрещён. Для huge можно оставить headers/fences через значительно меньший набор правил либо вообще временно detach highlighter и включать rich rendering только по явному действию.

   Отдельно надо runtime-trace проверить `setDocument(doc) + rehighlight()`: Qt attachment сам может инициировать работу highlighter, поэтому здесь потенциально платится ещё и повторная цена. Это уже надо подтвердить профилированием, а не объявлять догмой.

3. **FREEZE-003 — P0/P1: при каждом PROJECT TAB switch уничтожается весь document vahemälu (кэш).**
   `main.py:14420-14422`:

   ```python
   self.silo_docs = [None] * len(self.data["temp_presets"])
   self.archive_docs = [None] * len(self.data["archive_temp_presets"])
   ```

   Поэтому возвращение в уже открывавшийся тяжёлый project опять становится cold load.

   Потом `_switch_to_slot()` создаёт новый `QTextDocument`, делает `setPlainText`, подключает editor, highlighter, metadata и всё прочее.

   Это прямо объясняет сценарий: **A → B → A → B становится тяжёлым снова и снова**, хотя после первого прохода должно быть почти мгновенно.

   Нужен category-keyed document cache. Не надо держать 100 огромных QTextDocument без ограничений, иначе вылечим freeze и получим RAM-пожар. Нормальная архитектура: bounded LRU, например active document нескольких последних categories с лимитом по приблизительному размеру. Для тяжёлых силосов это даст громадную разницу.

   ```python

   ```

   Два разных QTextDocument вполне могут иметь одинаковый revision. Значит fingerprint silo A способен быть ошибочно принят как fingerprint silo B.


   Кроме того, `restore_silo_state()` на `2101-2103` опять делает:


   То есть обычное возвращение в silo опять означает full-copy + encode + CRC.

10. **FREEZE-010 — P2: refresh-функция архива содержит filesystem mutation.**
    `refresh_archive_panel()` начинается с `main.py:14621`:

    ```python

    ```

    А `_trim_archive()` на `14759+` не просто поправляет UI. Он ищет пустые slots, работает с directories, переносит folder в Trash, ведёт retirement transaction и rollback.

## Что я считаю реальной первопричиной

Это не один баг типа «Qt плохо работает с вкладками».

Это **cumulative synchronous work amplification**:

`click project`
→ extract outgoing full text
→ hash all bound silos
→ destroy document cache
→ rebuild incoming QTextDocument
→ full incoming text comparison
→ set document
→ full Markdown rehighlight
→ full checkbox/code scan
→ restore/fingerprint full scan
→ scan visible silo strings for line counts
→ scan them второй раз
→ unconditional preview full-text copy
→ archive refresh/filesystem check
→ incoming sync digest.

На больших silos эта цепочка превращает один innocuous click в небольшой offline render farm. Windows закономерно говорит: «ребята, ваше окно перестало отвечать».

## Порядок ремонта

Я бы не разрешал implementation agent начинать с микрооптимизаций regex. Сначала архитектура hot path.

**Phase 1:** встроить лёгкий phase profiler в `on_tab_changed()` и `_switch_to_slot()` с `time.perf_counter()`. Логировать только этапы >20–50 ms: `commit`, `sync`, `doc_load`, `attach`, `highlighter`, `restore_state`, `sidebar`, `preview`, `archive`. Добавлять chars/blocks/slot/category. Так на твоём Windows будет виден konkreetselt (конкретно) виновник каждого зависания.

**Phase 2:** убрать `slots=None` из project navigation, убрать повторный refresh, исправить `update_preview()` early return. Это дешёвые изменения с большим эффектом.

**Phase 3:** category-aware bounded document vahemälu и generation markers. Убрать `doc.toPlainText() != new_text`.

**Phase 4:** настоящий huge-document mode и оживить уже существующий `_LARGE_DOC_THRESHOLD = 500000`. На huge silo navigation не имеет права инициировать полный Live Preview regex pass.

**Phase 5:** unified `(doc_id, revision)` snapshot/fingerprint cache, checkbox metadata cache, line-count cache.

**Phase 6:** вынести `_trim_archive()` из refresh path и всё остальное disk-related из UI navigation.

Ключевой архитектурный invariant для агента я бы сформулировал жёстко:

> **Switching a category or silo must never perform work proportional to the combined size of sibling silos. After a document has been opened once, a warm switch back to it must perform no whole-document extraction, hashing, regex rehighlight, CRC, line recount, or filesystem reconciliation unless the document actually changed.**

Вот это и есть нормальная цель. Не «сделайте быстрее», а measurable contract.

Для regression suite я бы отдельно потребовал spy-тесты, что project switch не вызывает `_push_sync_files(slots=None)`, `refresh_temp_presets()` вызывается ровно один раз, `update_preview()` в Source/Live не читает `toPlainText()`, warm cached switch не делает whole-text equality, fingerprint различает два docs с одинаковым revision, а huge document не получает full rich-highlighter pass.

Runtime benchmark в этом sandbox я честно не могу снять: в окружении нет `PyQt6` (`ModuleNotFoundError`). Поэтому миллисекунды я из астрала не высасываю. Но статически перечисленные O(document)/O(project bytes) пути подтверждены непосредственно кодом. На твоей Windows-машине profiler после Phase 1 уже покажет процент вклада каждого из них.

И ещё важная штука: существующий `tests/test_markdown_highlighter_wave.py` проверяет, что large doc сохраняет headers и что `_sync_live_preview_highlighter()` вызывает один **явный** `rehighlight()`. Он не является performance-тестом и не доказывает отсутствие тяжёлой работы при `setDocument()`. То есть зелёные tests тут вполне могут улыбаться, пока GUI лежит мордой в асфальт. Классика software engineering, мать её.

Итоговый приоритет: **P0 сначала `_push_sync_files(all)` + highlighter + уничтожение doc cache.** Именно эта тройка наиболее правдоподобно объясняет твой конкретный «щёлкнул тяжёлую вкладку → Windows Not Responding». Остальные пункты затем уберут accumulating latency и сделают переключение действительно instant, а не «ну вроде теперь висит на секунду меньше».
