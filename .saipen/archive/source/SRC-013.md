[P0] [W2-001] src/fastprompter/core/instance_lock.py::bootstrap_ownership/_owner_is_stale/kill_pid - missing IPC ACK can forcibly terminate a legitimate live primary despite the mutex contract

EVIDENCE:
- instance_lock.py:1-29 defines the governing invariant explicitly: ownership belongs to a live PROCESS, not a responsive event loop; if another process owns the mutex and does not ACK IPC, the documented decision is UNRESPONSIVE and the second process must not become another writer.
- ipc_server.py:67-85 repeats the same contract: no ACK inside startup grace returns False and "the caller must exit, never become a second writer."
- main.py:19468-19471 likewise states that a live instance owning the database mutex must never be displaced merely because its event loop is quiet.
- The implementation contradicts all three contracts. instance_lock.py:394-420 interprets no ACK plus a matching owner record as a frozen process, calls kill_pid(pid), then polls the mutex and returns RECLAIMED once the killed owner's handle disappears.
- kill_pid() at instance_lock.py:234-275 invokes TerminateProcess and falls back to taskkill /F /T.
- _owner_is_stale() at lines 204-212 does not establish stale/dead ownership. It returns True specifically when the recorded process is still alive and its identity matches.
- Identity verification prevents killing an unrelated PID, but it cannot prove that killing the correct FastPrompter process is safe. A busy GUI thread, debugger stop, temporary I/O stall, modal/native blockage, or long scheduler callback remains a legitimate live database owner.
- tests/test_instance_lock.py:93-123 actively codifies the destructive behavior: a live owner with no IPC ACK is expected to be terminated and RECLAIMED.
- tests/test_instance_lock.py:162-172 explicitly labels a recorded live owner "eligible for frozen-process recovery" and expects _owner_is_stale() is True.
- Controlled production-code probe forced a valid live-owner identity, no IPC ACK, successful kill and second mutex acquire. bootstrap_ownership() returned:
  role=RECLAIMED
  reason="frozen owner 4242 process terminated; lock reclaimed"
  killed=[4242]
- Windows mutex WAIT_ABANDONED already supplies the safe OS-authoritative recovery mechanism when an owner actually dies; instance_lock.py:330-340 handles that path separately.

DEFECT:
The single-writer invariant has been inverted during recovery. "Unresponsive" has become "safe to terminate". A second launch can kill the authoritative FastPrompter process while it still owns unsaved RAM state and SQLite, bypassing the canonical final save and all orderly worker drains. The subsequent mutex acquire prevents simultaneous writers only by destroying the first writer, so split-brain protection has turned into a direct data-loss path.

REPAIR:
- Remove automatic kill/reclaim of a live mutex owner from bootstrap_ownership().
- If lock acquisition fails and IPC ACK is absent, return UNRESPONSIVE regardless of whether the recorded PID identity matches.
- Keep the owner identity record for diagnostics only, not as authorization to terminate a live process.
- Preserve WAIT_ABANDONED as the automatic crash-recovery path: actual process death lets Windows transfer mutex ownership without guessing liveness from UI responsiveness.
- If product requirements demand force-recovery, make it an explicit user-initiated destructive action with a clear unsaved-data warning, never an automatic startup transition.
- Remove or rename _owner_is_stale() so a live PID cannot semantically masquerade as stale.
- Update tests that currently require live-owner termination; the invariant test must instead require UNRESPONSIVE and zero kill calls.

VERIFY:
