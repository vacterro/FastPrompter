[P0] [CORE-001] src/fastprompter/main.py::_queue_silo_text_history / structural SILO transitions
EVIDENCE:
- The persistence layer explicitly defines stable silo_id as the recovery/history owner. Structural routes such as swap_temp_slots(), move_temp_to_index(), insert/delete remaps and cross-space swaps move silo_id with the logical SILO.
- _queue_silo_text_history(), however, reconstructs the previous committed text as:
  saved_by_key[(category, slot)] -> old content
  and then attaches any slot-coordinate difference to the CURRENT silo_id occupying that slot.
- This compares two different ownership epochs after any structural permutation: the previous content belongs to the previous identity at that coordinate, while silo_id_for() returns the post-remap identity.
- Exact-method reproduction using the unmodified _queue_silo_text_history body:
  previous committed slots: C[0]="A", C[1]="B"
  post-swap slots:         C[0]="B", C[1]="A"
  post-swap identities:    C[0]=SID-B, C[1]=SID-A
  queued transitions were:
    SID-B: "A" -> "B"
    SID-A: "B" -> "A"
  although neither SILO's text changed at all.
- The same coordinate mismatch applies to move, insert and delete: shifted survivors are interpreted as text edits because their previous text is read from the old occupant of the new slot.
- state._drain_silo_history_locked() durably stores those transitions in the same transaction as the structural result. Their after_hash then matches the current text, so validate_silo_lineage() cannot identify these fabricated transitions later.
- Existing tests/test_t1227_silo_integrity.py separately verifies identity movement and ordinary text-history behavior, but contains no structural-remap + history assertion; the two individually-green contracts therefore fail when composed.
DEFECT:
Pure structural operations manufacture cross-SILO text-history entries. After persistence/restart, persistent Ctrl+Z/Ctrl+Y can traverse text that belonged to another SILO and write it into the current SILO. The recovery mechanism therefore becomes a data-corruption mechanism despite stable identity remapping being correct.
REPAIR:
- Stop deriving recovery history by previous slot coordinate.
- Maintain/derive the previous committed content by stable silo_id for both normal and archive spaces.
- The previous side must use the previous COMMITTED identity mapping together with the previous committed slot rows; the current side must use the current identity mapping.
- Diff `{silo_id: committed_text_before}` against `{silo_id: current_text}`.
- A pure reorder/swap/move/category-space transfer of the same identity with unchanged text must queue ZERO text transition regardless of coordinate changes.
- A newly created identity has no predecessor transition.
- A deleted identity must not turn the successor's text into its transition.
- Preserve failed-save retry semantics: a rolled-back save must retain the exact pending legitimate transition without duplicating it, and the committed identity/content baseline must advance only after transaction success.
- Do not patch this by merely suppressing history around individual structural functions; ownership-aware history must be correct centrally so future structural routes cannot reintroduce the defect.

[P1] [PERF-001] PROVEN BOTTLENECK src/fastprompter/core/audio_render.py::device_ready_wav/_render_device_wav/_read_wav
EVIDENCE:
- The implementation intends to bound rendering with RENDER_MAX_SECONDS=30.0 on the requesting thread and RENDER_MAX_SECONDS_WORKER=120.0 on workers.
- The bound is checked too late. _render_device_wav() first calls _read_wav(path), and only after that full decode does it compute frames_in and compare it with the duration policy.
- _read_wav() calls wf.readframes(nframes) for the entire source, creates a second full array representation, expands every sample into Python float objects, and then constructs per-channel Python lists.
- The pure-Python frame-limit check is also after this expansion, so it does not bound decode memory either.
- device_ready_wav() additionally computes `_source_digest(path)` before entering _render_device_wav(), so a file that is guaranteed to be rejected for duration is still read end-to-end for hashing before being read end-to-end again for decoding.
- The equal-source-rate/edge-padding route returns through the branch before the shared duration check. `_wants_edge_pad()` prevents long files from ultimately being padded, but that decision is itself made only after the whole file has already been decoded.
- Controlled execution against the live module used a 10-second, 48 kHz, stereo, 16-bit WAV of 1,920,044 bytes and temporarily set the requesting-thread render limit to 0.1 s. The result was correctly `None`, but rejecting that file still consumed 0.9843 s and reached 43,130,943 bytes / 41.13 MiB of Python-traced peak allocation.

The render-duration policy is not a resource bound. Oversized audio is fully hashed and fully expanded into high-overhead Python sample structures before the code decides not to render it. - For an equal-rate source, decide edge-padding eligibility from header frame count before hashing/decoding; if no rendering/padding is needed, return None immediately.

- Keep a defensive frame ceiling inside `_read_wav()` itself, or pass an explicit max_frames argument and refuse before `readframes()`. This prevents a future direct caller from bypassing the preflight and recreating the same memory failure.
