[P1] [CORE-002] src/fastprompter/main.py::_shutdown_application / ui/qt_lifetime.py::drain_qt_threadpool

EVIDENCE:
- `_shutdown_application()` explicitly defines the invariant: shutdown timeout is fail-closed and the ownership mutex must remain held until process death rather than permitting a new primary while old workers can still publish: main.py:18761-18767.
- `drain_qt_threadpool()` documents that global-pool runnables execute Python, include external sync collection/silo counts/folder scans, and returns False specifically when its bounded wait expires: ui/qt_lifetime.py:28-47.
- The shutdown call site repeats the intended ordering invariant: global-pool runnables must drain before any writer, DB handle, or lock is retired so late results cannot touch torn-down state: main.py:18791-18794.
- Actual timeout handling violates both contracts. On `drain_qt_threadpool() is False`, main.py:18795-18798 only logs `"proceeding after bounded wait"`; it neither sets `clean = False` nor refuses teardown.
- Execution therefore continues through logical finalization, window close, worker/IPC/SQLite retirement, and finally reaches `lock.release()` whenever the unrelated later shutdowns report clean: main.py:18800-18969.
- Isolated execution of the exact `_shutdown_application` production AST with `drain_qt_threadpool() -> False` and all other finalizers successful produced `result=True` and `lock_released=True`.
- This is the direct opposite of the function's documented fail-closed behavior.

DEFECT:
A timed-out global QThreadPool drain is treated as informational rather than a shutdown failure. FastPrompter can explicitly release its single-primary writer mutex and destroy/close application-owned state while Python runnables known to be alive are still executing. That reopens the class of stale-result/use-after-teardown/access-violation failures the shutdown protocol claims to prevent, and can allow a new primary process to start before the old process has actually become quiescent.

REPAIR:
- Make global-pool drain status part of the canonical clean-shutdown gate.
- `drain_qt_threadpool() == False` must make clean shutdown impossible.
- Preserve the useful logical final-save step if it can be performed safely, but do not proceed into resource retirement that contradicts the fail-closed contract while the global pool is still live.
- At minimum, a drain timeout must prevent window destruction and `lock.release()`. Prefer an explicit refused-finalization branch before writer/DB/IPC retirement so the code matches its own ordering comment.
- Keep the mutex owned until process death on this path, exactly like the existing refused-finalization and dirty-worker paths.
- Log the timeout as ERROR/CRITICAL, not a warning saying shutdown will proceed.
- Do not weaken the bounded drain into an unbounded wait; the existing timeout exists to prevent a wedged runnable from hanging exit forever.

VERIFY:
- Regression with `drain_qt_threadpool() -> False`: `_shutdown_application()` returns False; `lock.release()` is never called; `window.deleteLater()` is never called; unsafe writer/DB retirement after the failed pool gate is not performed.

[P0] [W2-001] src/fastprompter/core/instance_lock.py::bootstrap_ownership/_owner_is_stale

EVIDENCE:
- The module's primary ownership invariant states that ownership belongs to a live PROCESS, not a responsive event loop, and that a process failing mutex acquisition knows a live owner exists and "must not touch the DB": instance_lock.py:1-12.
- Its documented decision table says mutex held + IPC no ACK => UNRESPONSIVE, "do NOT become a second writer": instance_lock.py:22-29.
- ipc_server.request_show() independently states the same boundary: the mutex is authoritative; no ACK within the startup grace returns False and "the caller must exit, never become a second writer": ipc_server.py:67-80.
- main_entry() again states that if a live instance owns the database mutex, the newcomer must not open another writer "no matter how quiet its event loop is": main.py:18674-18688.
- `_owner_is_stale()` contradicts those contracts. Despite its docstring claiming "did not acknowledge IPC within grace AND its recorded identity matches", its implementation contains no IPC/grace state. A recorded PID that is alive and identity-matched is sufficient to return True: instance_lock.py:204-212.
- After any failed IPC handoff, bootstrap_ownership() labels that live owner frozen, calls kill_pid(), polls the mutex for up to three seconds, and returns RECLAIMED if acquisition succeeds: instance_lock.py:373-420.
- `kill_pid()` uses Windows TerminateProcess and falls back to `taskkill /F /T`: instance_lock.py:234-275.
- The existing OS mutex implementation already has the correct dead-owner recovery primitive: WAIT_ABANDONED grants ownership only after the previous owner actually dies and records `lock.abandoned`: instance_lock.py:317-343.
- FastPrompter explicitly includes a GUI watchdog because real event-loop stalls greater than 1.5 seconds occur and need diagnosis: main.py:281-352. A stall lasting through request_show's grace therefore falls directly into this automatic-kill path.
- Existing tests encode the unsafe behavior rather than catching it: test_instance_lock.py:93-123 expects a live frozen owner to be killed/reclaimed; test_instance_lock.py:162-172 declares a recorded live owner reclaimable.
- Exact-production behavioral probe: first mutex acquire=False, IPC handoff=False, verified recorded live PID=4242, kill succeeds, second acquire=True. Actual result:
  role=RECLAIMED
  killed=[4242]
  reason="frozen owner 4242 process terminated; lock reclaimed"

DEFECT:
IPC responsiveness has been incorrectly promoted from a user-interface signal into authority to kill the process that already owns the writer mutex. A legitimate primary whose GUI is temporarily blocked, whose IPC token is temporarily inconsistent, or whose IPC server fails to answer inside the grace period can be forcibly terminated by merely launching FastPrompter again. TerminateProcess/taskkill bypass the primary's canonical logical finalization, so unsaved editor/silo state and other RAM-only work can be lost. The replacement may then acquire the abandoned mutex and become primary, making this a destructive recovery policy rather than prevention of split-brain. Identity verification proves which process owns the record; it does not prove that killing that live owner is safe.

REPAIR:
- Restore the declared invariant: after initial mutex acquisition fails, an unacknowledged IPC handoff must return UNRESPONSIVE and must never automatically call kill_pid().
- Remove automatic live-owner termination/reclamation from normal bootstrap_ownership().
- Remove `_owner_is_stale()` or restrict it to diagnostics; a live identity-matched owner must not mean stale.
- Preserve IPC ACK behavior: ACK => HANDED_OFF.
- Preserve genuine crash recovery through the OS mutex. WAIT_ABANDONED is already the authoritative signal that the previous owner died and ownership was transferred.
- Preserve `lock.abandoned` database validation before normal writes.
- If forced termination remains a desired product capability, keep it outside automatic startup and require an explicit destructive user action with a clear unsaved-data warning. After termination, rely on the mutex's abandoned/death semantics rather than treating no-ACK itself as ownership release.
- Rewrite the existing tests that currently require killing a live no-ACK owner.

VERIFY:

- Live mutex owner + IPC server unavailable/token mismatch => role UNRESPONSIVE; kill_pid is never called.
